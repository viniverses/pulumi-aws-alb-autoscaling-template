# IAM permissions for deployment

[Back to README](../README.md)

The IAM user or role behind your AWS CLI profile needs permission to create, read, update, and delete the resources in [src/iam.ts](../src/iam.ts). These permissions must be granted before running Pulumi; the template does not grant permissions to the identity deploying it.

| Purpose                                                                       | IAM actions                                                                                                                                                                                |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Manage the EC2 role and its trust policy                                      | `iam:CreateRole`, `iam:GetRole`, `iam:UpdateRole`, `iam:UpdateAssumeRolePolicy`, `iam:DeleteRole`                                                                                          |
| Manage role tags                                                              | `iam:TagRole`, `iam:UntagRole`, `iam:ListRoleTags`                                                                                                                                         |
| Attach and remove the AWS-managed SSM policy; inspect existing policies       | `iam:AttachRolePolicy`, `iam:DetachRolePolicy`, `iam:ListAttachedRolePolicies`, `iam:ListRolePolicies`                                                                                     |
| Manage the EC2 instance profile and role membership                           | `iam:CreateInstanceProfile`, `iam:GetInstanceProfile`, `iam:AddRoleToInstanceProfile`, `iam:RemoveRoleFromInstanceProfile`, `iam:DeleteInstanceProfile`, `iam:ListInstanceProfilesForRole` |
| Manage instance profile tags                                                  | `iam:TagInstanceProfile`, `iam:UntagInstanceProfile`, `iam:ListInstanceProfileTags`                                                                                                        |
| Pass the EC2 role when creating or updating the ASG with its Launch Template  | `iam:PassRole`                                                                                                                                                                             |
| Allow AWS to create its default service-linked roles on first use, if missing | `iam:CreateServiceLinkedRole`                                                                                                                                                              |

Scope role permissions to `web-ssm-role-*` and instance profile permissions to `web-instance-profile-*` in the deployment account. The suffixes are generated by Pulumi. Restrict policy attachment permissions to the AWS-managed policy `arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore` using the `iam:PolicyARN` condition where supported. Read/list actions that do not support resource-level permissions require `Resource: "*"`.

For example, the following statement grants only the role-passing part of the deployment permissions. Replace `<ACCOUNT_ID>` with your AWS account ID:

```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::<ACCOUNT_ID>:role/web-ssm-role-*",
  "Condition": {
    "StringEquals": {
      "iam:PassedToService": "ec2.amazonaws.com"
    }
  }
}
```

When granting `iam:CreateServiceLinkedRole`, restrict `iam:AWSServiceName` to `autoscaling.amazonaws.com` and `elasticloadbalancing.amazonaws.com`. This permission is needed only when the corresponding default service-linked role does not already exist.

These IAM actions supplement the infrastructure permissions; they are not a complete deployment policy. The deployment identity also needs `ssm:GetParameter` to resolve the Amazon Linux AMI and the relevant EC2, ELB, Auto Scaling, and CloudWatch lifecycle actions. Auto Scaling validates related permissions such as `ec2:RunInstances` and `ec2:CreateTags` when using the Launch Template. Organization SCPs, permissions boundaries, and session policies can further restrict effective access.

The role created for the EC2 instances has `AmazonSSMManagedInstanceCore` attached so SSM Agent can communicate with Systems Manager. It is separate from the deployment identity. Users opening a terminal session need their own Session Manager permissions, such as `ssm:StartSession`, scoped to the intended instances and session documents.

References: [Auto Scaling Launch Template permissions](https://docs.aws.amazon.com/autoscaling/ec2/userguide/ec2-auto-scaling-launch-template-permissions.html), [IAM instance profiles](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_switch-role-ec2_instance-profiles.html), [Auto Scaling service-linked roles](https://docs.aws.amazon.com/autoscaling/ec2/userguide/autoscaling-service-linked-role.html).
